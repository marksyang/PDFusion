# 文字編輯：實作方式與限制

PDF 的文字不是「可選取的資料」，而是一連串繪圖指令（內容流）。要「修改文字」
本質上有兩種做法：

1. **真正重建**：把該頁內容流完整解析、改動文字物件、重新序列化。
   幾乎沒有成熟的開源 JS/TS 函式庫支援（pdf-lib 不支援）；PDFium 也不提供
   對外的編輯 API。
2. **覆蓋重繪（本專案採用的方式）**：
   - 用 PDFium 取出該文字段落的座標、字型名稱與大小；
   - 用 PDFium 抽出原內嵌字型的原始位元組（TTF/OTF）；
   - 用 pdf-lib 在該位置畫一個白色矩形「蓋住」舊字；
   - 再以 pdf-lib `embedFont()` 嵌入原字型、`drawText()` 重繪新文字。

## 為什麼這樣做

- 對一般文件（字型有內嵌、版面簡單）視覺上幾乎無縫：新文字與原文字
  使用同一個字型檔案。
- 完全在 pdf-lib 公開 API 內完成，不需要手動改寫 PDF 內部結構。
- 對任何 PDF 檢視器都相容（內容就是標準繪圖指令）。

## 已知限制

| 情境 | 行為 / 限制 |
|---|---|
| 編輯範圍 | 以「文字段落（segment）」為單位，非字元 / 單字級。整段被替換。 |
| 背景 | 舊字以白色矩形覆蓋。若原文在彩色 / 圖片背景上，會露出一塊白底。 |
| 字型缺失 | 若原字型無法抽取（無內嵌、CFF 特殊格式等），降級為 Helvetica。 |
| 多行 / 換行 | 新文字按 `\n` 分行重繪；縮排、對齊與原段落格式不保證一致。 |
| 座標近似 | 基線位置以 ascent ≈ 0.8×行高 估算；某些字型可能略有垂直偏移。 |
| 加密 / 特殊字碼 | 部分 PDF 使用自訂字碼表（CMap），重繪後若缺少對應映射會顯示異常。 |
| 無還原 | 烘焙進內容流後無法用本程式「 Undo 」舊文字（請先另存一份）。 |

## 適用與不適用

- ✅ 適合：白底文件、常見內嵌 TTF 字型（報告、合約、簡報导出件）的
  小幅度文字更正。
- ⚠️ 不適合：掃描文件（無文字層）、複雜版面（多欄、旋轉頁面）、
  彩色背景上的文字、需要精確排版的正式出版流程。

## 旋轉頁面（/Rotate）

- 渲染、文字擷取、搜尋、註解繪製皆使用「視圖空間」（套用 /Rotate 後、左上原點），與螢幕顯示一致。
- 烘焙（bake）與文字編輯會將視圖座標換算回 pdf-lib 的未旋轉 user space，因此註解/文字會出現在正確位置（E2E 已驗證 /Rotate 90）。
- 新輸入的文字（free text / 改字）在旋轉頁上會以**視圖方向**繪製（水平可讀、與螢幕顯示一致）：
  內部用 raw content stream + 旋轉矩陣（`textedit/RotatedText.ts`），因為 pdf-lib 的高層 drawText 無法旋轉文字。
- 已知限制：
  - 旋轉頁上的新文字使用標準字型（或原文嵌入字型的 raw 引用），無法自動換行到下一「列」以外的版面流程（同非旋轉頁的 overlay 編輯限制）。
  - PDFium 不支援 /Contents 陣列內的 inline stream，故低層路徑必須用 `context.contentStream()` + `context.register()` 建立 indirect stream。
